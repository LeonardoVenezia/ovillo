# DECISIONS — Ovillo

Decisiones técnicas, en orden cronológico (spec §10: ante ambigüedad, decidir y registrar acá en vez de frenar).

## 2026-10-16

- **D-001 — Next.js 16 (App Router), no 15.** Es el LTS activo; Next 15 entra en EOL el 21/10/2026. Turbopack es el default.
- **D-002 — pnpm como gestor de paquetes.** Ya instalado (10.x) en la máquina; reproducible y veloz. Nota: pnpm 10 bloquea scripts `postinstall` por defecto; si una dependencia los necesita (p. ej. `sharp`), correr `pnpm approve-builds`.
- **D-003 — Sin carpeta `src/`.** La estructura sigue la spec §10: `app/`, `components/`, `features/<módulo>/`, `db/`, `lib/`.
- **D-004 — Validación de env con Zod, lazy (`getEnv()` en `lib/env.ts`).** Valida en la primera consulta real: el build y CI no dependen de secretos; en runtime falla temprano con mensaje claro. Por ahora la única requerida es `DATABASE_URL`; las de Fase 2 en adelante se activan cuando su módulo las use.
- **D-005 — Cache Components + Partial Prefetching activos** (default del scaffold de Next 16). Modelo del proyecto: datos públicos compartidos → `"use cache"` + `cacheLife()` + `cacheTag()`; datos por usuario o runtime → `<Suspense>` o `"use cache: private"`; invalidación → `updateTag()` (read-your-writes, desde Server Actions) y `revalidateTag(tag, profile)` (el 2.º argumento es obligatorio en 16). Nada de datos sin cachear fuera de Suspense: el build lo bloquea.
- **D-006 — shadcn/ui con preset `radix-nova`** (Radix como pide la spec; íconos Lucide). La generación nueva usa el paquete unificado `radix-ui` y `cn` (del paquete `cn`) en vez de `clsx` + `tailwind-merge`: no agregar esos dos.
- **D-007 — Tipografías: Fraunces (títulos) + Inter (texto)**, vía `next/font/google` con variables CSS. La spec permitía alternativas; estas mantienen el tono "taller cálido y editorial".
- **D-008 — Modo oscuro con `next-themes`** (clase en `<html>`, default "sistema"). El ícono del toggle se intercambia con `dark:` en CSS en vez de estado de React: evita hydration mismatch y el lint `react-hooks/set-state-in-effect`.
- **D-009 — Base de datos: Drizzle + driver `neon-http`** (`@neondatabase/serverless`), tablas/columnas en `snake_case` (opción `casing` en drizzle-kit y en el cliente), migraciones solo con `generate` + `migrate` (nunca `push`). Los scripts de datos corren con `tsx` + `dotenv`.
- **D-010 — Test de contraste WCAG AA que lee `app/globals.css`.** `lib/design/contrast.test.ts` parsea el CSS real (24 pares, claro y oscuro) y falla si algún par baja de 4.5:1: la paleta no se puede degradar sin que lo note el CI.
- **D-011 — El registro npm por defecto de esta máquina (verdaccio, `~/.npmrc`) da 502 con `drizzle-orm`.** Se instaló (y se actualizará) con `--registry=https://registry.npmjs.org/`. Anotado en `AGENTS.md`.
- **D-012 — Identidad git por proyecto.** El proyecto vive en la cuenta personal `LeonardoVenezia` (email `leovenezia@outlook.com.ar`, distinto del email global del trabajo). Se usa un `core.sshCommand` **local del repo** que fuerza la llave `~/.ssh/id_ed25519_leonardo` ignorando la config SSH global (`-F /dev/null`), mismo patrón que el proyecto hermano `list`. El resto de la máquina sigue usando la cuenta del trabajo.
- **D-013 — `pnpm typecheck` corre `next typegen` antes de `tsc`.** Los tipos de rutas (`LayoutProps`, `PageProps`, `RouteContext`) solo se generan con `next dev`, `next build` o `next typegen`. En un checkout limpio (CI) `tsc --noEmit` fallaba con `Cannot find name 'LayoutProps'`; ahora el script los genera siempre. El workflow de CI no cambia: sigue corriendo `pnpm typecheck`. El primer CI en GitHub falló además porque `pnpm/action-setup@v4` chocaba con `version: 10` en el YAML + `packageManager` en `package.json`; se quitó el `version` del workflow (el action lee el pin del `package.json`).
- **D-014 — Deploy en Vercel + Neon vía la integración gestionada por Vercel.** El sitio vive en <https://ovillo-sepia.vercel.app> (plan Hobby) y la base es un proyecto **Neon** creado desde Vercel (Storage → Neon → "Create New Neon Account"), conectado a los 3 entornos del proyecto. El `DATABASE_URL` local se copió desde el panel de Neon a `.env.local` (gitignoreado); la cuenta es gestionada por Vercel, así que el `neon login` del CLI no aplica (para operar la base: "Open in Neon" desde Vercel). Además, los scripts (`db:check`, `drizzle.config.ts`) ahora cargan `.env.local` y luego `.env` **explícitos** (`dotenv/config` a secas solo lee `.env`; Next en runtime sí carga `.env.local` solo).

## 2026-10-17 (Fase 2 — cuentas)

- **D-015 — Arrancamos con email + contraseña; Google OAuth queda para más adelante** (pedido del dueño). Better Auth ya lo soporta a futuro sin cambiar el modelo de datos: se suma como otro proveedor en `account`.
- **D-016 — La instancia de Better Auth es lazy (`getAuth()`), y el CLI usa `lib/auth-cli.ts`.** El handler de `/api/auth/*` también resuelve la instancia por request (`toNextJsHandler((req) => getAuth().handler(req))`). Así el build y CI siguen sin necesitar secretos (sostiene D-004): `pnpm build` verificado sin `.env.local`. Para regenerar el esquema del auth: `pnpm dlx auth@latest generate --config lib/auth-cli.ts --output db/auth-schema.ts` (correr con `.env.local` cargado en el shell).
- **D-017 — Emails transaccionales con plantillas propias (`lib/email.ts`), sin React Email por ahora.** Son dos plantillas; el costo de la dependencia no se justifica todavía. Los envíos se programan con `after()` de Next (fuera del ciclo de respuesta, no demoran el request) y sin `RESEND_API_KEY` en desarrollo se registran en consola para poder probar igual.
- **D-018 — Mientras no haya dominio propio, Resend va en modo de prueba:** remitente `onboarding@resend.dev` y entregas solo a la casilla dueña de la cuenta Resend. Alcanza para desarrollar y probar todo el flujo. Comprar el dominio (~USD 10–15/año) sigue pendiente de decisión del dueño; `EMAIL_FROM` ya deja el lugar listo.
- **D-019 — Sesión 100 % server-side:** DAL en `lib/session.ts` (`getOptionalUser` con `"use cache: private"`; `requireUser` redirige al ingreso). Toda UI que lee la sesión vive bajo `<Suspense>` (guía "Authentication with Cache Components" de Next 16). `proxy.ts` hace solo la redirección optimista con `getSessionCookie` (sin tocar la base); la validación real es siempre contra la base en cada página protegida.
- **D-020 — Plugin `username` de Better Auth:** normaliza el @usuario a minúsculas y guarda `displayUsername`. El formulario de registro consulta disponibilidad en vivo (debounce de 450 ms, descartando respuestas viejas) contra `/api/auth/is-username-available`. El tipo inferido de Better Auth no siempre refleja los campos que agrega el plugin, así que `lib/session.ts` los lee con un cast defensivo y comentado.
- **D-021 — Por ahora una sola base Neon (la de Vercel) para desarrollo y producción**, porque todavía no hay usuarias reales. Antes de abrir el registro al público: crear una rama de Neon para desarrollo (también la van a usar los e2e). Anotado en PROGRESS.
- **D-022 — Una migración inicial (`0000`) con las tablas de Better Auth** (`user`, `session`, `account`, `verification` + índices y FKs con cascade), generada por el CLI y aplicada con `pnpm db:migrate`. `db/auth-schema.ts` no se edita a mano: para extender las tablas se configura en `lib/auth.ts` (plugins, campos adicionales) y se regenera.

## 2026-10-17 (Fase 2 — bienvenida y perfil)

- **D-023 — El perfil público vive en `app/[username]` (segmento dinámico raíz), no en una carpeta `@[usuario]`.** En App Router las carpetas que empiezan con `@` son "slots" de rutas paralelas y no generan URL, así que `/@usuario` se sirve desde ese segmento: acepta con y sin arroba, normaliza a minúsculas y lo desconocido termina en **404 real**. Ojo: el valor del segmento llega percent-encoded (`%40maria`) y hay que decodificarlo. La ruta lleva `instant = false` (guía `instant`): la URL recién se conoce en la petición —la barra inferior usa `usePathname`— y además el chequeo de existencia corre antes de transmitir para que el estado 404 sea de verdad. Hoy lee la base sin cachear; cuando haya tráfico pasa a `"use cache"` + `cacheTag` (D-005).
- **D-024 — Onboarding de 2 pasos por ahora (salteable).** La spec §5.1 pide 3, pero el tercero ("sugerencia de 3 grupos y 5 personas para seguir") necesita grupos y personas que todavía no existen: llega con el módulo Comunidad. El asistente guarda con Server Action (`saveOnboarding`) y precarga lo elegido. El registro redirige a `/bienvenida`, y "Mi tejido" recuerda terminarlo mientras `crafts` esté vacío.
- **D-025 — Tabla `profile` según spec §6** (bio, location, country, crafts[], skill_level, links jsonb, default_visibility, theme, reduce_motion), 1 a 1 con `user` y cascade al borrar la cuenta. `theme`/`reduce_motion` quedan vacías hasta que exista sincronización de preferencias. Límites: bio 160 y ubicación 80 caracteres. `links` es `[{ kind: "instagram" | "web", url }]` normalizado y validado (acepta `@usuario`, usuario pelado o URL); la UI maneja dos ranuras y el formato queda listo para más tipos.
- **D-026 — Privacidad simple: `default_visibility` `"publico" | "privado"`.** En privado la página muestra solo avatar, nombre, @usuario y fecha de alta; el dueño se ve completo con la etiqueta "Solo para mí". La granularidad por sección y el estado `seguidores` del contenido llegan con la fase de privacidad.
- **D-027 — Contadores y pestañas del perfil, pospuestos.** "Proyectos terminados" / "años tejiendo" (spec §5.2) necesitan proyectos y una fecha de inicio de tejido que aún no existen: por ahora el perfil muestra "Se sumó en <mes año>". Las pestañas (Proyectos, Guardados, Grupos, Actividad) llegan con sus módulos.
